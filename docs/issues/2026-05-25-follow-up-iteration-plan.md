# 后续迭代优化计划：查询性能与异地录分刷新问题

## 背景

当前 GuanDan V2.0 已完成 Redis runtime、录分链路、大屏展示和移动端展示等多轮修缮优化。后续还有两个需要继续排查和优化的问题：

1. 数据库查找、检索语句仍有优化空间。
2. 本机多页面并发测试写分不卡顿，但其他主机登录网站写分后，前端显示有时必须按 F5 才会重新请求后端并刷新；暂不确定是 frp、网络链路还是代码刷新机制问题。

## 目标

- 降低后台管理、录分、对阵查询和统计接口的数据库压力。
- 找出“异地主机写分后前端不自动刷新”的真实原因，避免只凭现象误判。
- 给比赛现场保留稳定兜底：即使网络短暂波动，也能明确提示或自动恢复，而不是让用户依赖手动 F5。

## 迭代拆分

### 1. SQL 查询与索引审计

- 梳理高频入口：`/api/admin/overview`、`/api/admin/matches`、`/api/score/table`、`/dashboard_snapshot`、旧模板页的对阵和录分查询。
- 对仍会访问 MySQL 的路径补充耗时日志，记录 SQL 类型、参数规模、耗时和调用入口。
- 使用 `EXPLAIN` 检查 `fight_info`、`mini_team_info`、`team_info`、`team_level` 等关键表查询。
- 优先处理明确低风险项：缺失索引、可拆分的 `OR` 联表、重复查询、可由 Redis runtime 读模型承接的查询。
- 输出一份 SQL 优化清单，区分“可直接改代码”和“需要迁移/建索引窗口”的项。

### 2. 录分刷新链路诊断

- 在前端请求层记录 `/dashboard_snapshot` 的发起时间、完成时间、失败原因、是否超时和最近一次成功快照时间。
- 在后端为 `/dashboard_snapshot`、`/api/admin/scores`、`runtime_view_refresh_service` 增加轻量诊断日志，串起一次写分后的 dirty 标记、异步重建和前端读取。
- 分三种访问路径复现：本机 localhost、局域网 IP、frp/公网地址。
- 对比三条链路的请求是否发出、是否到达后端、后端是否返回新 `snapshot_updated_at`、前端是否正确落入状态更新。
- 如果是网络/frp 超时，优化提示与重试；如果是前端轮询中断，修复轮询恢复；如果是后端 dirty 刷新延迟，优化 dirty worker 或必要时增加提交后主动刷新策略。

### 3. 用户体验兜底

- 在录分页提交成功后显示“已提交，等待大屏刷新”的明确状态，并避免重复提交。
- 大屏如果连续多次轮询失败，显示轻量网络状态提示，但保留本地倒计时和榜单轮播。
- 后台管理页提供最近快照更新时间，便于现场判断是否是数据没变、刷新慢，还是网络断连。

## 验收标准

- 后端相关 unittest 通过。
- 前端 `npm run build` 通过。
- 能用同一套诊断日志说明：一次异地主机写分后，前端是否发起了刷新请求、后端是否返回了新快照、页面为何没有更新。
- SQL 优化至少形成一份可执行清单；如涉及索引或表结构调整，需要单独列出迁移风险。

## 注意事项

- Redis 仍作为运行态事实源，不能为了短期排查恢复高频 MySQL 读取。
- 不要把 frp、网络、防火墙和代码 bug 混为一个问题；先用日志确认请求到底停在哪一层。
- 涉及中文日志、说明和计划文档时保持 UTF-8 编码，避免 PowerShell 读取时出现乱码。
